# Gravity Drop: notes for Claude

A gamified marble-race name picker. The user felt online wheel spinners lacked a physical, clicky feel and pick-from-a-hat tools weren't exciting. They asked for a **gravity race with lots of comebacks**, where the leader keeps changing because of things that spin, blow and move, not just static pegs. Keep that goal in mind for every change: more lead changes and more visible, clicky drama. The win odds must stay even.

The README covers setup, the deploy steps and the folder layout. The notes below are what the code doesn't show.

## Architecture rules
- **`src/sim/` must stay headless.** No Pixi and no DOM. The renderer and audio only read sim state and drain `sim.events`. That separation is what lets `scripts/fairness.ts` and `scripts/inspect.ts` run in Node.
- **Determinism.** The sim advances only in fixed `DT = 1/120` steps, and everything random uses `sim.rng` (mulberry32 seeded from `opts.seed`). The countdown is also counted in sim steps (`COUNTDOWN`), not wall-clock time. Never use `Math.random()` or real time inside `src/sim/`; doing so breaks "Replay this race". Slow motion (`timeScale` in `main.ts`) only changes how many steps run per frame.
- **Fairness.** Start slots are shuffled, and nothing in the sim ever picks a marble by name or index. Chaos events (lightning, lucky warps) were removed at the user's request: races are pure physics, so lead changes have to come from the course itself.
- **Coordinates.** 1 unit ≈ 1 m and y points down. The course is `W = 16` wide, with a gate at y = 4, followed by stacked segments, the finish funnel and a basin. Walls are capsules (rounded joints, so marbles never snag). Collision handles are tagged via `sim.tag()` to drive sounds and bumper behaviour.
- **Race length** is a count of random segments, 1–15 (`MIN_SEGMENTS`/`MAX_SEGMENTS` in `course.ts`), with the finale added on top. Short/Medium/Epic are presets of 5/10/15 (`SEGMENT_COUNTS`). `SimOptions.length` takes a preset name or a number, and `segmentCount()` in `sim.ts` resolves and clamps it. The setup screen stores a number and migrates old saved preset names. There are only 9 segment templates, and `pickSegments` reuses them (never back-to-back), so a long race repeats sections.
- **Adding a segment.** Add a template to `TEMPLATES` in `course.ts`, built only from `Builder` primitives and zones, then run the stall checks below.
- **Adding a finale.** Finales live in `FINALES` in `course.ts`, separate from the segment templates. Each one has `h` (including the basin), `finish` (the finish line's offset) and a `build` function, and usually ends with `finishFunnel()` (the slingshot funnel with a short flipper at the bottom of each wall, the finish line and the basin). `buildCourse` always draws one rng value to pick a finale, so a seed builds the same segments whichever finale is forced (`SimOptions.finale`, the setup screen's Final drop setting, or the fairness script's 7th argument). The finales are `pinball` ("FINAL DROP") and `mayhem` ("FINAL MAYHEM", which uses most obstacle types).

## Traps hit so far
- **Infinite loops in segments.** Fans that covered a whole ramp and outpowered gravity pinned marbles against a wall forever, and reversing belts plus pop-back boosters recycled them. The rule now: force zones cover only a *window* of a ramp, belts are weak (`0.025` blend per step), and back-boosters have long cooldowns. There are two safety nets: an anti-stall nudge after 3.5 s motionless, and a `rescue()` after 20 s with no progress (counted in `sim.rescues`). Keep rescues rare, about 0.05–0.3 per race.
- **No top-level `await` in `main.ts`.** Pixi lazy-loads chunks that import back into the entry module, so a top-level await deadlocks the *production* build (a blank page with no errors). Startup lives in `async function boot()`.
- **Funnels.** With `opts.funnels`, `buildCourse` adds a 5.5 m funnel to the bottom of every segment except the last (it is counted in that segment's `h`) and picks a guard from `FUNNEL_GUARDS`. It only draws from the rng when funnels are on, so old seeds without funnels still build the same course. Never put a spinner *above* a throat: its tips batted marbles back up the funnel slope forever (rescues went from 0.05 to 1.5+ per race). Guards must keep the throat moving; never use a static plug, and must fit inside `FUNNEL_H` (the paddle wheel once reached into the next segment and swept through its pegs).
- **Removed sections.** The Factory, The Elevator and Pinball Parlor were taken out at the user's request, and Windmill Alley was merged into the Windmill Grinder. Conveyors are now only used by the Mayhem finale, and flippers by the finales. Stampers and the lift are unused: the user removed them from Mayhem along with its trapdoors.
- **Teleports reset the no-progress clock.** A back-portal or a lift ride restarts `bestY`/`bestT` from the new spot. Before that, a marble sent back was "rescued" (dropped forward) after 20 s if it had not caught up, which undid the setback. It made Mayhem look like it needed 0.38 rescues per race; the real figure is 0.
- **Mayhem tuning.** Its trapdoor floor, stamper and lifts were removed at the user's request. Both ramps in part 6 have belts running inwards. Below them, at the user's request: three side-by-side funnels (throats 2.0 m wide), then two portals swaying together one throat apart, so at each end of the sweep they sit under two throats at once (at the user's request; they send marbles back to just above the see-saw, y 17.4, not to the finale's top: the user found the full trip back too harsh). Their exits move too (`PortalZone` `exitPatrol`): each sweeps its own half, x 1.5–7.5 and 8.5–14.5, mirroring the other, then 5 peg rows above the finish funnel. The windmill that used to guard the gap between the ramp ends was removed. The top has a row of 4 pendulums under the pegs (they replaced 4 boosters the user found weak), and everything below sits `MAYHEM_TOP` = 1.6 m lower to make room. Part 4 has a bumper between the shelves in place of the old crosswind fan; its wall ledges were removed at the user's request. Under the 3 peg rows below the see-saw sit two Glass Tiles floors with a peg row between them (`glassFloors()` with `glassTiles(rng, 2)`), and everything from the three funnels down sits `MAYHEM_GLASS` = 6.2 m lower. The see-saw rocks at 2.0–3.0 rad/s (doubled from 1.0–1.6 at the user's request; 600 races chi² 3.6, 0 rescues, 13.9 lead changes). Tested: 600 races chi² 6.7, 0 rescues, 13.6 lead changes; 30 names with funnels 0.27 rescues.
- **Funnel flippers.** `finishFunnel()` puts a 1 m flipper at the bottom of each funnel wall. The drain between their tips stays about 3.5 m wide and they flick every 1.6-2.4 s; tested with no extra rescues. The Pinball finale also has two short, quick flippers (every 0.9-1.4 s) fed by short bars on the walls, at least 1.1 m clear of every bumper.
- **Windmill Grinder** (id `grinder`). It is alternating rows of windmills, with one big windmill and two medium ones in the middle and no funnel (the user asked for the hopper to be removed). Windmill tips stay at least 0.9 m from each other and from the walls, so nothing gets pinched.
- **Portal Maze.** Two back-portals patrol a peg-free row (`PortalZone` with `patrol`), each sweeping its own half at a constant speed. About 27% of marbles get sent back per maze.
- **Glass Plug funnel guard** (id `glass`). A single `breakaway()` pane across the throat: the first marble is launched back up the funnel (kick 7.5–8.5, apex ≈ 1.8 m with g = 18, inside the 3 m funnel) and the pane is gone, so it's never a lasting plug. Adding it changed the guard shuffle, so funnels-on seeds from before it build different courses. Tested: 600 short races with funnels, chi² 2.3, 0 rescues; 30 names, 0.47 rescues per race.
- **Rows of bumpers act as a ceiling.** A horizontal row of bumpers with gaps of about 1 m kicks nearly every marble back up. One near the Final Drop's funnel caused about 1.4 rescues per race. Keep gaps within a row at 1.5 m or more.
- **30-name runs.** Most of their roughly 1.3 rescues per race come from the pile waiting at a `valve` funnel guard. That's a known, separate issue, not caused by any single section.
- **Start mixer.** The start box (`mixer()` in `course.ts`) has a lid at `sim.mixerTop` and four sweeping floor jets (`FanZone.until`/`sweep`) that run only during the countdown. It is built *after* the segments so seed → course layout didn't change. Plain alternating jet tilts only made marbles bounce in place (about 90% of left-to-right order survived); the sweep brings that down to about 62% with 6 marbles. During the countdown the camera holds on the box, the standings board is frozen and no crown is shown.
- **Final Drop slingshots.** `Builder.sling()` kicks marbles off its upward-facing side on contact start (handled in `marbleHit`, like bumpers). On the funnel walls only the middle stretch is a slingshot; the plain wall next to the throat lets marbles settle out instead of being kicked back and forth. The Final Drop absorbed the old Pinball Parlor: its spread-out bumper diamond sits over slingshots on both side walls, and below it are two evenly spaced rows of 4 and 5 bumpers, about 3.8 m apart vertically, with plain deflector bars (no kick) on both walls between them. The user wants the bumpers well spaced, so spread them out rather than adding more. Slingshot bars in the middle between the rows were tried: they juggled marbles against the row above (1.3 rescues per race) and were removed at the user's request. The bumper x's are chosen so the field leaves no straight drop: rows that repeat the same x's leave lanes that fall straight into the throat. When moving a bumper, check that every x between the side slingshots touches one (|x − bx| < r + MARBLE_R), that the throat (x 6.1–9.9) is covered squarely, and that gaps between bumpers stay wide. Leave flippers out of this section: anything that moves above the throat bats marbles back up.
- **Trampoline Park pads.** `Builder.tramp()` pads re-launch marbles off their top face (handled in `marbleHit`). The first tuning had marbles hopping sideways from pad to pad along a single row: each bounce carried them about as far as the gap between pads, and crossing the segment took about 9.6 s. Keeping the bounce speed low (3.5 m/s minimum, 5.5–6.5 m/s cap) and the sideways carry at 0.75 brought that down to about 5.6 s. Keep the highest bounce (v²/2g) below the 2.2 m spacing between rows, so a marble can't bounce back up onto the row above.
- **Pendulum Swing** (id `pendulums`). `Builder.pendulum()` hangs a bumper ball on a rod. Only the ball is solid: the rod collider is a sensor with `NO_GROUPS`, kept only so the renderer can draw it (the user asked that marbles pass through the rods). A bumper tag can carry `collider`/`kick`/`swing`, so `marbleHit` reads the ball's live position and adds its swing velocity. The kick is soft (6.5–7.5 m/s against the usual 11) so marbles aren't juggled back up into the row 2.6 m above. Rows of 4 and 3 balls alternate; swinging balls stay about 0.9 m apart and from the ledges. The walls use fixed ledges only (short ones on the rows of 4, 2.6 m ones on the rows of 3), so nothing within 3.5 m of a wall is ever open. Moving balls leave a middle lane open for a moment now and then, but in 600 test passes no marble fell through without hitting something.
- **Glass Floors / Glass Tiles** (ids `glass`, `glasstiles`, built by `glassFloors()`). These are the "equalizer" sections: 4 floors of `Builder.breakaway()` glass. The first marble to land on a pane's top face is launched up at 8–9 m/s, and the pane stops colliding for good (`NO_GROUPS`, so the collider handle stays valid) and emits `shatter`. Glass Floors uses one full-width pane per floor. Glass Tiles splits each floor into 1–4 tiles, never the same count on two floors in a row. Tiles always span the whole width with 0.2 m seams, so nothing drops past a floor untouched. A sparse peg row sits between floors, and the highest bounce (~2 m) reaches it but never the floor above. Measured over 150 races: they are the only sections where the pack comes out tighter than it went in (time spread ×0.8, against ×1.2–1.8 elsewhere), and the leader changes across them about 62% of the time, with 0 rescues.
- **Peg fields and the walls.** Peg rows end about 0.5 m short of each wall, which left a lane where a wall-hugging marble fell straight through untouched. `pegRows()` now adds wall deflectors between every other pair of rows (when there are 2+ rows), leaves out pegs within 1.05 of a deflector so nothing can wedge, and adds one peg past each deflector tip to cover the gap that leaves. Check new peg layouts for straight-drop lanes by testing each x against the static colliders in the band.
- **Photo-finish slow motion** (`isDramatic` in `main.ts`). In first-to-finish it triggers when the leader is in the last 7 m and the runner-up is under 2 m or about 0.3 s behind. It eases in fast and holds 0.9 s past the line. The old 5 m / 1.6 m test with slow easing missed some close finishes; the new one caught all 23 close finishes in a 400-race test.
- **Continue watching.** The winner card's "Continue watching" button sets `watching`: the camera follows whoever is still racing, and a 🏆 Results button reopens the card. The card comes back on its own 1.5 s after the last marble finishes, and then the camera stays on the last finisher. With no target at all, the camera drifts back to the start gate.
- **Section guide and previews.** The setup card's 📖 Section guide (`src/ui/sections.ts`) lists every entry in `SECTIONS` (`course.ts`: segment templates, finales, funnel guards) with a description, and its Preview shows one on the main stage as the `'preview'` screen in `main.ts`. `SimOptions.section` makes the sim build only that section via `buildSection()` (no gate, mixer, countdown or marbles; `finishY` is Infinity unless it's a finale). `renderer.preview` frames the whole section, or auto-pans and lets the player wheel/drag when it's taller than about 30 m. A new template, finale or guard shows up in the guide automatically but needs a description in `ABOUT` in `sections.ts`.
- **Winner history.** Up to 100 winners are kept in `gd.history`. The setup card shows the latest 5, and "Show all" opens a `<dialog>`, which has the clear-all button behind a confirm step. While the dialog is open, the global hotkeys in `main.ts` are skipped (`setup.modalOpen`), so Space can't start a race behind it.
- **Rendering.** Static walls and pegs share one Graphics object. The zone layer must draw *above* static walls, or the conveyor belts get hidden. Name labels are drawn in screen space (overlay) so text stays crisp.
- **Standings.** The HUD reorders with hysteresis (needs a 0.35 m lead to swap places) and `sim.leader` also has hysteresis, so neck-and-neck marbles don't flicker. In last-one-standing the board is "SAFEST FIRST" (hindmost on top) and crowns only show in first-to-finish mode.

## Verifying changes
- `npx tsc --noEmit` then `npm run build`.
- Fairness and stuck checks: `npm run fairness -- 600 short first 6 5000` (args: races, length (preset or 1–15), mode, names, seedOffset, funnels 1/0, finale random/pinball/mayhem). Expect chi² under the printed bound, **0 timeouts**, and about 5–12 lead changes per race. Also check `last` mode, `medium` length, 30 names and funnels on after any physics or course change. A single high chi² can be noise, so rerun with a different seedOffset before chasing a bias.
- One seed in detail: `npx tsx scripts/inspect.ts <seed> [length] [names] [seconds] [funnels]` prints the segment layout, event counts and final marble positions (useful for finding where marbles get stuck).
- Visual check: run `npx vite preview --port 4173` and screenshot with `puppeteer-core` driving the installed Chrome (`C:/Program Files/Google/Chrome/Application/chrome.exe`, args `--use-angle=swiftshader --enable-unsafe-swiftshader`). Install puppeteer in the scratchpad, not in this project. Preset settings via `localStorage` key `gd.settings`, e.g. `{"length":"short","mode":"first"}`, and names via `gd.names`. Check both 1600×900 and 390×844 (phone). Headless frame rates of about 20–50 fps are normal with software rendering.

## Environment quirks (Windows, Git Bash tool)
- `node -e '…'` has silently done nothing in this shell. Write a script file and run that instead.
- `pgrep` isn't available, and sed replacements containing `$&` mangled code once. Prefer the Edit tool for code changes.
