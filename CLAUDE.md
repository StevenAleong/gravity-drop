# Gravity Drop: notes for Claude

A gamified marble-race name picker. The user felt online wheel spinners lacked a physical, clicky feel and pick-from-a-hat tools weren't exciting. They asked for a **gravity race with lots of comebacks**, where the leader keeps changing because of things that spin, blow and move, not just static pegs. Keep that goal in mind for every change: more lead changes and more visible, clicky drama. The win odds must stay even.

The README covers setup, the deploy steps and the folder layout. The notes below are what the code doesn't show.

## Architecture rules
- **`src/sim/` must stay headless.** No Pixi and no DOM. The renderer and audio only read sim state and drain `sim.events`. That separation is what lets `scripts/fairness.ts` and `scripts/inspect.ts` run in Node.
- **Determinism.** The sim advances only in fixed `DT = 1/120` steps, and everything random uses `sim.rng` (mulberry32 seeded from `opts.seed`). The countdown is also counted in sim steps (`COUNTDOWN`), not wall-clock time. Never use `Math.random()` or real time inside `src/sim/`; doing so breaks "Replay this race". Slow motion (`timeScale` in `main.ts`) only changes how many steps run per frame.
- **Fairness.** Start slots are shuffled, and nothing in the sim ever picks a marble by name or index. Chaos events (lightning, lucky warps) were removed at the user's request: races are pure physics, so lead changes have to come from the course itself.
- **Coordinates.** 1 unit ≈ 1 m and y points down. The course is `W = 16` wide, with a gate at y = 4, followed by stacked segments, the finish funnel and a basin. Walls are capsules (rounded joints, so marbles never snag). Collision handles are tagged via `sim.tag()` to drive sounds and bumper behaviour.
- **Race length** is a count of random segments, 1–15 (`MIN_SEGMENTS`/`MAX_SEGMENTS` in `course/index.ts`), with the finish added on top (the setup screen says "segments + finish"). Short/Medium/Epic are presets of 5/10/15 (`SEGMENT_COUNTS`). `SimOptions.length` takes a preset name or a number, and `segmentCount()` in `sim.ts` resolves and clamps it. The setup screen stores a number and migrates old saved preset names. There are only 12 segment templates, and `pickSegments` reuses them (never back-to-back), so a long race repeats sections.
- **Custom courses** (user's request). The setup screen's Course setting is 🎲 Random (the default: `length` random segments) or 🛠 Custom: the player's own list of up to 15 sections, in order and with repeats (back to back too), saved as `settings.custom` (section ids) and passed as `SimOptions.segments`, which replaces `pickSegments`. A custom course draws nothing from the rng for the pick, and the random path draws exactly as before (300-race fairness output was identical before and after). The builder (`src/ui/course.ts`) reorders with ▲/▼ or by dragging the grip; its drag listeners sit on `window`, because moving the row in the DOM drops pointer capture. Courses can be saved and loaded like name lists (localStorage `gd.courses`, name → ids). History entries store `segments`, so replays rebuild the course. While Custom is on, the stage beside the setup card shows a **course preview** instead of the demo race (`SimOptions.preview`: the whole course without gate, mixer or countdown, marbles dropping in at the top as in a section preview, up to `COURSE_PREVIEW_MAX` = 48, plus 2 dropped at the top of every section on the first step so the camera, panning at `COURSE_PAN` = 7 m/s, never shows an empty course). 👁 Preview course shows it full screen on the `'preview'` screen (`previewKind` `'course'`; Back goes to setup, not the guide). Tested with repeats: 300 short of glass×2, foosball×2, pinball×2, chi² 1.8; 300 last-one-standing of pendulums×2, glass, sliders, 3.9; 100 races of 6 sections with 30 names and funnels on, 19.4 (0.28 rescues); 150 races of a 15-section course with every section doubled back to back, 7.4 (79 s races, 0.01 rescues); 0 timeouts.
- **Analytics** (user's request: is anyone using it, and with which options). Umami Cloud, picked over Google Analytics because it is cookieless (no consent banner). The script tag in `index.html` reports only from `data-domains` (the GitHub Pages domain), so tests and dev runs send nothing. Events go through `track()` in `src/ui/analytics.ts`, called only from `main.ts` (see the README for the events). Never send names, only counts, and keep tracking out of `src/sim/` (it would also change `__SIM_VERSION__`).
- **Course files.** `src/sim/course/`: `index.ts` (generator, `SECTIONS`, `buildSection`), `types.ts` (`Template`, `Finish`), `helpers.ts` (`pegRows`, glass floors), `funnels.ts` (funnel guards), `mixer.ts`, and one file per segment in `segments/` and per finish in `finishes/`. The order of `TEMPLATES` (`segments/index.ts`) and `FINISHES` (`finishes/index.ts`) decides every seed's course, so keep it when editing.
- **Builder components.** `src/sim/builder/index.ts` is the `Builder` class: shared helpers (`kinematic`, `arm`, `hinge`) and a list of components (`windmill = windmill;`). Each component is a function with `this: Builder` in its own file (`builder/windmill.ts`, `builder/foosball.ts` with `FOOS_PARTS`, …); related ones share a file (`wall`/`ledge`, `trapdoor`/`hatch`, `blasts`/`mine`, `blackHole`/`vortex`). A new component needs its file plus a line in the class.
- **Zones.** `src/sim/zones/` has one file per zone class (`fan.ts`, `conveyor.ts`, `blackhole.ts` with the vortex types and `vortexAt`, `blast.ts` with `Mine`/`Blast`, …), shared helpers (`cycle`, `sweep`, `Patrol`) in `util.ts`, and `index.ts`, which re-exports them and defines the `Zone` union. Import from `'../zones'`. A new zone needs its file, its exports in `index.ts` and a place in `Zone`.
- **Adding a segment.** Add a file in `course/segments/` and append it to `TEMPLATES`, built only from `Builder` primitives and zones, then run the stall checks below.
- **Finishes.** Every course ends with a finish from `FINISHES` (`funnel`, the slingshot funnel with a short flipper at the bottom of each wall, `halfpipe` and `freefall`) straight under the last segment. A finish has `h` (including the basin), `finish` (the finish line's offset) and `build`, and holds the finish line and the basin. Its top must leave room for whatever the last segment ends in. `buildCourse` always draws one rng value to pick it, so a seed builds the same segments whichever is forced (`SimOptions.finish`, the setup screen's Finish setting, or the fairness script's 7th argument). It is its own HUD segment, named `FINISH · <name>`.
- **No more finales** (user's request). There used to be a finale between the segments and the finish: Final Pinball (now the `pinball` segment template, "PINBALL") and Final Mayhem (removed completely, along with the setup screen's Final drop setting and the fairness script's finale argument). Removing them changed every seed's course. Tested after: 600 short chi² 2.0 (25.7 s races, down from ~36 s; 9.7 lead changes, down from 12.7, as Mayhem was a big source of them); each finish forced, 300 short, chi² 0.8–6.9; 600 last-one-standing 4.8; 300 medium 1.8 (16.2 lead changes); 100 races with 30 names 31.4 (bound 44.2); 600 short with funnels 4.8. All 0 rescues, 0 timeouts.
- **Half-pipe finish** (id `halfpipe`, added on the user's request as a variant; not yet fairness- or stall-checked). A Λ roof sends everyone out to the walls, then a parabolic bowl (2.4 m deep, 8 capsule segments a side) slopes down to a drain hole 1.4 m clear (so two marbles can't arch across it). A fast marble jumps the hole and swings up the far side; a slow one drops in. The roof sits above the rims, so a swinging marble can't reach it.
- **Free Fall finish** (id `freefall`; the user's idea: the feeling of going really fast without a really long drop). It's 40 m to the line (the user doubled it from 20 m). A `SkyZone` (`Builder.sky()`) covers the whole finish down to the line. It cancels gravity and eases each marble's fall toward 2.5 m/s (`ease` 0.012 per step, so extra speed bleeds off over about 0.7 s), and adds a gentle sideways gust that varies with height and time. Sideways speed has its own light damping (`drag`, `FREEFALL_DRAG` = 0.001 per step, a half-life of about 6 s): the user wanted marbles that come in at an angle to keep it, instead of straightening into a vertical drop (it used to be `ease * 0.5`). Marbles now bounce off the side walls often (about 3 in 4 get within 0.8 m of one), but nothing pins them there. The renderer draws speed lines streaking up through it at about 30 m/s, so the slow fall reads as fast.
- **Free Fall boost pads rise** (user's request: fixed pads broke the illusion of speed). A `RiserZone` (`Builder.risers()`) spawns 0.6 m tall downward pads, each randomly single (1.4 m) or double (2.8 m) width (`FREEFALL_PAD_WS`, user's request; it was all 1.4, then all 2.8; the renderer adds a chevron column per 1.4 m of width) (10 m/s, keeping the marble's sideways speed) at random x along its bottom edge every 0.3–0.7 s, and they stream up at 20 m/s (`FREEFALL_RISE`, the slow end of the speed lines) until they leave the top. Spawns come from the zone's own `mulberry32`, seeded with one draw of the build rng, and its clock counts sim steps, so replays match. Pad centres are spread over the full width and then pushed back inside, so wall-riders meet as many pads as anyone (with plain uniform x they got 1.42 boosts against 1.62). Because the pads move much faster than the marbles, how many a marble meets hardly depends on its own speed, so one boost doesn't make the next more likely. Each pad boosts a given marble once (`RisingPad.boosted`), but a different pad re-boosts it even mid-boost, resetting it to full speed (user's request; a zone-wide 0.8 s cooldown used to swallow back-to-back pads). In the free fall the renderer swaps a marble's trail for racing effects (`drawSlipstream()`): wind streaks off its back and a nitro flame while it's going faster than cruising. A 4× longer trail was tried and dropped. A new pad stays out of the columns (with a 0.3 m margin) of pads spawned in the last `FREEFALL_CLEAR` = 1.2 s, about 24 m above it (user's request: pads kept spawning in the lane of the one before). It retries up to 8 times, drawing from the zone's own rng, and gives up after that. Over 200 races: back-to-back boosts (two within 1 s) fell from 0.68 to 0.15 per marble, boosts per marble 2.88 → 2.83, marbles with none 1.3% → 0.3%, 2+ boosts 87% → 94%, and wall-side marbles still meet as many pads (2.93 per marble against 2.76 in the middle). Tested with it forced: 600 short chi² 3.6; 100 with 30 names 29.0; funnels on 3.3; 0 rescues, 0 timeouts. Last-one-standing was noisy: 12.7, 9.4, 12.6, 11.5, 8.1, 0.5 on six seed offsets, with a different name on top each time, and 8.7 pooled over all 3,600 races. The old pads (`FREEFALL_CLEAR` = 0, the same draws) gave 3.7, 5.8, 11.5 on the first three. With the random widths: 100 short chi² 2.6, 4.0 lead changes, 0 rescues; the stats below are from all-2.8 m pads. That replaced fixed rows (2 per row, 4 m apart, never in the column the row above used), which were spaced out to make chaining harder. Measured over 200 races with 2.8 m pads: 2.92 boosts per marble (1.91 with 1.4 m pads), none get zero, 93% get 2 or more, 9.0 s spent in the finish. Tested with it forced at 2.8 m: 600 short chi² 2.2 (31.9 s races, 9.8 lead changes); 600 last-one-standing 4.8; 100 with 30 names 36.8 (bound 44.2; 32.0–38.6 at 1.4 m); funnels on 3.3. 0 rescues, 0 timeouts. There's no funnel at the user's request: marbles fall straight to the line, with only the usual basin below it. With the old 20 m version the first marble into the finish still won about 81% (90% for the funnel, 76% for the half-pipe), because the leader usually arrives over a second ahead; that hasn't been re-measured since the changes.
- **Rejected finishes.** The user tried and removed a Water Wheel (a slow 8-spoke windmill; the first marble in won only 58%, but it "wasn't sparking joy") and a Ski Jump (a takeoff over a pit, where fast marbles overshot onto a landing hill and had to roll back; not the feeling the user wanted). The stats were fine for both; what the user is after is how a finish *feels*, so check with them before tuning a finish for numbers alone.

## Traps hit so far
- **Infinite loops in segments.** Fans that covered a whole ramp and outpowered gravity pinned marbles against a wall forever, and reversing belts plus pop-back boosters recycled them. The rule now: force zones cover only a *window* of a ramp, belts are weak (`0.025` blend per step), and back-boosters have long cooldowns. There are two safety nets: an anti-stall nudge after 3.5 s motionless, and a `rescue()` after 20 s with no progress (counted in `sim.rescues`). Keep rescues rare, about 0.05–0.3 per race.
- **No top-level `await` in `main.ts`.** Pixi lazy-loads chunks that import back into the entry module, so a top-level await deadlocks the *production* build (a blank page with no errors). Startup lives in `async function boot()`.
- **Funnels.** With `opts.funnels`, `buildCourse` adds a 5.5 m funnel to the bottom of every segment except the last (it is counted in that segment's `h`) and picks a guard from `FUNNEL_GUARDS`. It only draws from the rng when funnels are on, so old seeds without funnels still build the same course. Never put a spinner *above* a throat: its tips batted marbles back up the funnel slope forever (rescues went from 0.05 to 1.5+ per race). Guards must keep the throat moving; never use a static plug, and must fit inside `FUNNEL_H` (the paddle wheel once reached into the next segment and swept through its pegs).
- **Removed sections.** The Factory, The Elevator, Pinball Parlor and the Portal Maze were taken out at the user's request, and Windmill Alley was merged into the Windmill Grinder. Flippers are used by the Pinball segment and the funnel finish. Conveyors, stampers, the lift, the see-saw and portals are unused since Final Mayhem was removed; their `Builder` primitives are kept.
- **Teleports reset the no-progress clock.** A back-portal or a lift ride restarts `bestY`/`bestT` from the new spot. Before that, a marble sent back was "rescued" (dropped forward) after 20 s if it had not caught up, which undid the setback.
- **Funnel flippers.** The funnel finish puts a 1 m flipper at the bottom of each funnel wall. The drain between their tips stays about 3.5 m wide and they flick every 1.6-2.4 s; tested with no extra rescues. The Pinball segment's flippers flick every 1.0-1.6 s.
- **Windmill Grinder** (id `grinder`). It is alternating rows of windmills, with one big windmill and two medium ones in the middle and no funnel (the user asked for the hopper to be removed). Windmill tips stay at least 0.9 m from each other and from the walls, so nothing gets pinched.
- **Switch Maze** (id `switches`; it replaced the Portal Maze, which the user found to be just a peg garden with portals). A funnel feeds a flip-flop switch (`Builder.toggle()`: a plate pivoted at its centre and tilted 0.6 rad), which feeds two funnels with a switch each, then four 4 m lanes in a shuffled order: two glass floors (no pegs between, at the user's request), pegs with wall ledges, a 3-bar windmill, or three zigzag shelves. A switch flips when a marble *enters* the band under its open tip (entry only, so a slow marble can't flip it twice); marbles that arrive mid-swing pass without flipping it (about 1.6 flips per marble against a maximum of 2). Traps found while building it: gaps just under a marble's width between lane pegs or shelves and the walls stalled marbles, so every gap is either ≥ 0.75 m clear or closed; and two marbles arched across a throat (one hanging on the throat wall, propped on one sitting on the plate) for 10+ s, which is why the throat walls are only 0.3 m and the plate sits 1.5 m below the throat. Glass pane bounces (~2.25 m) must stay below the switch's trigger band. At the user's request the top funnel's two walls carry speed floors (express belts: `conveyor` with `reverses: false`, `SPEED_FLOOR` = 13 m/s, blend 0.05), stopping short of the throat. They raise the speed through the top throat from 6.7 to 10.9 m/s; in a 6-minute preview, 709 marbles through, median 5.4 s (was 6.0), max 14.8 s, 0 rescues. Races after: 600 short chi² 3.0 (9.1 lead changes); 600 last-one-standing 1.9; 300 medium 3.3; 100 with 30 names 27.2 (0.08 rescues); funnels on 1.7. 0 timeouts. Earlier test before the belts: 600 short races chi² 3.3, 0 rescues, 12.7 lead changes; 30 names 0 rescues.
- **Black Hole** (id `blackhole`; the user's idea: marbles spinning round a gravity well, smashing into each other and getting sucked in). One `BlackHoleZone` with a `Vortex` (`Builder.vortex()`) over a round bowl centred on the hole (so the floor follows the field; ramps from the walls close the gaps at its rims), open on top so a marble can fall straight in. Swallowed marbles drop out under the bowl and carry on. A vortex is `rings` (outermost first) blended over `blend` m, the outermost also fading in from plain space at its edge. Each ring has a pull that grows as r/d inward (so its orbit speed √(accel·r) is the same across it), a `spin` target that eases each marble's speed round the centre **in whichever direction it's already going** (the user disliked marbles being yanked round to one fixed direction; two-way orbits also mean head-on smashes), and `grav`, the share of normal gravity left. Things learned tuning it: a swirl *force* keeps adding speed (marbles circled forever), so spin is a target kept just under orbit speed; marbles riding the bowl wall with spin applied circled forever too; and full gravity squashes every orbit so marbles dived in on the first pass, which is why the orbit ring keeps only 10% of it. The user tried three rings (an outer drift ring) and preferred two: an orbit ring out to the bowl (15 m/s² at 7.7 m, spin 10.4 against an orbit speed of 10.75, `grav` 0.1) and an inner ring (spin 4, no gravity) that **grows** (`VortexGrowth`, user's catch-up idea): it starts at 1.3 m / 70 m/s², and once the hole swallows a marble it grows over 5 s to 75% of the orbit ring's radius (5.8 m) at 55 m/s² (still ~310 m/s² by the horizon), shrinking back once the well has been empty for 3 s. Growth runs on sim time, not swallow count, so it behaves the same with 6 or 30 names. In races the first marble in spends ~5 s in the hole and the last ~2.6 s (6 names), and 43% of pairs leave in the opposite order to how they went in (27% with 30 names). The camera holds on the hole and zooms out to fit the well while its target is inside (`renderer.vortex`, released 1 m past the well's edge), instead of bobbing with the orbiting leader. Tested: 600 short chi² 8.4 and 6.9 (rerun); 600 last-one-standing 4.6; 300 medium 4.7; 100 with 30 names 24.8; funnels on 0.6; blackhole×2 300 short 8.2 and 6.2 (rerun); last-one-standing of blackhole, pegs, blackhole 1.0; blackhole×2 with 30 names 36.2 (bound 44.2); funnels on with blackhole, pinball, blackhole 2.1. 0 timeouts, ≤ 0.01 rescues per race. Adding it to `TEMPLATES` changed every seed's course.
- **Minefield** (id `mines`, a **draft**; the user's idea: the pegs explode, throwing marbles up, down or sideways in a radial blast, and a blown peg is gone for a while). The pegs are a `BlastZone`'s mines (`Builder.blasts()` returns the zone; `Builder.mine()` adds a peg that the zone draws, not the static layer, so it can vanish). Every 0.08–0.16 s (`MINE_GAP`) a random ready peg is lit: it glows for 0.7 s (`MINE_FUSE`), then blows (collider to `NO_GROUPS`). Its shockwave (radius 2.2–3.0 m, `MINE_R`, spreading over 0.1 s) sets each marble it reaches to 25% of its old velocity plus 14 m/s (`MINE_KICK`) straight away from the peg, fading to 45% at the rim; each blast throws a marble once. The peg comes back after `MINE_DOWN` = 2 s once no marble overlaps its spot. Which peg and when come from the zone's own `mulberry32` (one draw of the build rng) and never look at marbles. The sim emits `blast` (sparks, boom) and `blasted` per throw. Layout (user's request: no wall ledges, evenly spaced pegs, pegs by the walls): 11 staggered rows 1.5 m apart, pegs 1.56 m apart; even rows run wall to wall with their outer pegs 0.2 m off the wall (closing the wall lane; a marble landing on one rolls off inward), odd rows sit in the gaps with ~0.83 m clear by the wall, and two rows cover every x. 116 pegs, about 22 gone at any time. Measured over 60 races of pegs → mines → pegs with 6 names: 2.75 throws per marble (36% up, 32% down, 31% sideways), 9% untouched, 5.0 s in the section (max 9.9 s), the first marble in comes out first 42% of the time (58% for plain pegs). Tuning history: blasts at random spots rather than pegs were tried first (4.4 throws per marble at 11 blasts/s); with pegs as mines at 3 s down time and a sparser grid, 60% of the pegs were gone at once. Tested: mines×2 300 short chi² 2.3; 300 last-one-standing of mines, pegs, mines 3.7; 100 mines×2 with 30 names 39.8; funnels on with mines, pinball, mines 2.8; 300 of pegs, mines, glass, mines, sliders 3.3. 0 rescues, 0 timeouts. Taking `draft` off puts it in the random rotation and changes every seed's course.
- **Peg Garden jams with a full pack** (fixed). With 30 names, a course opening with `pegs` jammed at the first wall deflector: two marbles arched across the gap between its tip and the peg below, 5–6 piled on top, and they were rescued ~20 s in (0.41 rescues per race on pegs, glass, pegs, last-one-standing). Starting the pegs 1 m lower only cut that to 0.11; leaving out the top deflector pair moved the jam to the next one down; pulling the tip peg in to close the gap made it worse (0.44–0.57). What worked (user's request: a bigger segment with rows spaced out): `PEG_GAP` 1.4 → 1.9 m, the first row 2 m down (`PEG_TOP`), and no deflectors on the first two rows (`pegRows`' `deflectFrom`, `PEG_DEFLECT` = 2). The section is 24.5 m tall (was 18). 0 rescues over 300 races with 30 names (pegs, glass, pegs; pegs, mines, pegs; pegs×3); with the top deflectors kept, 0.00–0.06. Tested after: 600 short chi² 1.1 (26.5 s races, 3.6 lead changes); 600 last-one-standing 12.0, then 3.0 and 4.3 at other seed offsets; 300 medium 8.1; 100 with 30 names 32.6; 600 short with funnels 3.3; pegs×2 300 short 3.8. 0 rescues, 0 timeouts. This changed the geometry of every course with a Peg Garden (not the rng draws).
- **Draft sections.** A template or finish with `draft: true` shows in the section guide (and, for templates, the course builder) but is never picked at random, and `buildCourse` rolls the finish from the non-draft ones, so adding a draft doesn't change any seed's course. The Minefield is a draft at the moment. The user removed the **Event Horizon** finish, a draft that was a deep bowl with a black hole over its lowest point (a plain `BlackHoleZone`, no vortex) as the only way to the line.
- **Black holes without a vortex.** `BlackHoleZone` / `Builder.blackHole()`: a back-portal horizon inside a gravity well whose pull rises toward the centre, with a sideways swirl, optionally drifting along a `Track`. It emits a `portal` event with `hole: true` (its own effect and ticker text). It was tried in "Black Hole Switchbacks" (zigzag ramps); the user liked the obstacle but not the section. A hole 1.35 m above a ramp with a 2.2 m well and 34 m/s² pull swallowed about 0.4 marbles per pass. Its drawing is done in a scaled-up local frame, because Pixi tessellates circles by local radius and world-unit circles looked polygonal.
- **Glass Plug funnel guard** (id `glass`). A single `breakaway()` pane across the throat: the first marble is launched back up the funnel (kick 7.5–8.5, apex ≈ 1.8 m with g = 18, inside the 3 m funnel) and the pane is gone, so it's never a lasting plug. Adding it changed the guard shuffle, so funnels-on seeds from before it build different courses. Tested: 600 short races with funnels, chi² 2.3, 0 rescues; 30 names, 0.47 rescues per race.
- **Rows of bumpers act as a ceiling.** A horizontal row of bumpers with gaps of about 1 m kicks nearly every marble back up. One near the finish funnel (under the old Final Pinball) caused about 1.4 rescues per race. Keep gaps within a row at 1.5 m or more.
- **Valve funnel guard** (id `valve`). At the trapdoors' usual open angle (1.35 rad) its door tips were left about 1.1 m apart, narrower than two marbles side by side (1.28 m). Pairs jammed there until the doors closed and knocked them back up the funnel, which also caused most of the roughly 1.3 rescues per race in 30-name runs. At the user's request the doors now open further (`VALVE_SWING` = 1.65 rad, a touch past straight down, through `trapdoor()`'s `swing` argument) and stay open longer (62–72% of each cycle, up from 50–60%). In a 6-minute preview test, 684 marbles got through instead of 450, 29 were knocked back up instead of 132, and there were 0 rescues instead of 10. With funnels on: 300 short races chi² 6.0, 300 last-one-standing chi² 7.1, and 100 races with 30 names chi² 35.0 (bound 44.2) at 0.10 rescues per race.
- **Plain funnel guard** (id `plain`, added at the user's request): an empty throat. Adding it changed the guard shuffle again, so funnels-on seeds build different courses than they did before.
- **Start mixer.** The start box (`mixer()` in `course/mixer.ts`) has a lid at `sim.mixerTop` and four sweeping floor jets (`FanZone.until`/`sweep`) that run only during the countdown. It is built *after* the segments so seed → course layout didn't change. Plain alternating jet tilts only made marbles bounce in place (about 90% of left-to-right order survived); the sweep brings that down to about 62% with 6 marbles. During the countdown the camera holds on the box, the standings board is frozen and no crown is shown.
- **Pinball** (id `pinball`; rebuilt at the user's request to look like a real machine). The playfield is rows of 2, 1, 2, 3, 2 bumpers, all r 0.6 and widely spaced (the user wants them big and spread out, not more of them), with plain bars on the walls at y 4.8 and 10.6 that turn wall-huggers back in. The lower table starts at `PINBALL_LOW` = 13.5: on each side an inlane guide runs from 1 m off the wall down to a 1.5 m flipper's hinge, so the guides funnel everything to the flippers and a drain ~2.2 m clear between their tips. A `Builder.sling()` stands in front of each flipper, off the walls, with ~0.85 m of inlane clear behind it (the user wanted marbles able to go behind the slings). The gap between the wall and each guide is an outlane (~0.85 m clear, open below) that lets a lucky marble skip the flippers: about 9% of marbles take one (the wall bars keep it low). In a 10-minute preview test: median 5.5 s through the section, max 24 s, 0 rescues. Full races after the rebuild: 600 short chi² 5.0 (9.3 lead changes); 600 last-one-standing 6.9; 300 medium 0.8; 100 with 30 names 41.6 (bound 44.2); funnels on, 600 short 2.3 and 100 with 30 names 14.6 (0.08 rescues). 0 timeouts. `Builder.sling()` kicks marbles off its upward-facing side on contact start (handled in `marbleHit`, like bumpers); the funnel finish also uses slings on the middle stretch of its walls, leaving the wall by the throat plain so marbles settle out instead of being kicked back and forth.
- **Trampoline Park pads.** `Builder.tramp()` pads re-launch marbles off their top face (handled in `marbleHit`). The first tuning had marbles hopping sideways from pad to pad along a single row: each bounce carried them about as far as the gap between pads, and crossing the segment took about 9.6 s. Keeping the bounce speed low (3.5 m/s minimum, 5.5–6.5 m/s cap) and the sideways carry at 0.75 brought that down to about 5.6 s. Keep the highest bounce (v²/2g) below the 2.2 m spacing between rows, so a marble can't bounce back up onto the row above.
- **Pendulum Swing** (id `pendulums`). `Builder.pendulum()` hangs a bumper ball on a rod. Only the ball is solid: the rod collider is a sensor with `NO_GROUPS`, kept only so the renderer can draw it (the user asked that marbles pass through the rods). A bumper tag can carry `collider`/`kick`/`swing`, so `marbleHit` reads the ball's live position and adds its swing velocity. The kick is soft (6.5–7.5 m/s against the usual 11) so marbles aren't juggled back up into the row 2.6 m above. Rows of 4 and 3 balls alternate; swinging balls stay about 0.9 m apart and from the ledges. The walls use fixed ledges only (short ones on the rows of 4, 2.6 m ones on the rows of 3), so nothing within 3.5 m of a wall is ever open. Moving balls leave a middle lane open for a moment now and then, but in 600 test passes no marble fell through without hitting something.
- **Foosball** (id `foosball`; for the user's foosball events, where it picks gift-card winners). There are 8 rods, as on a real table (`FOOS_RODS`): 3, 2, 3, 5, 5, 3, 2, 3 players, coloured black, black, yellow, black, yellow, black, yellow, yellow, 3.3 m apart. `Builder.foosRod()`: at the user's request each player looks like a real table's man (domed cap, smiley face, chest block on the rod with flanges, one leg with a slot, ridged block foot). Its colliders are `FOOS_PARTS` (ball head, round-cuboid chest and foot, capsule leg; the foot is barely wider than the leg, so nothing rests on it), and the renderer's `foosman()` draws the whole figure from one sensor marker at the pivot (`Shape` kind `foosman`), so keep the two in step. Only the players are solid (the rod is a drawn sensor). A rod slides its players as one with a wandering sway (top speed ~1.3 × 1.8–2.6 m/s). At the user's request there are no wall ledges: the end player's flanges come to within 0.25 m of the wall, so the wall lane is only open while the rod is away and a lucky marble can slip down the side. Each rod kicks every 0.9–1.4 s (the user asked for more kicks; it was 1.3–2.1 s, and a kick's swing takes 0.7 s, so there's little room left), swinging its feet up 0.9 rad toward the far wall; each step the swing is clamped so the foot stays 0.9 m off that wall and the head (which swings the other way) 0.1 m off the near one. Kicks emit `flip`. At the bottom only (user's request), a goal: funnel walls from 0.9 m below the goalies' feet down to a mouth W/3 wide, with a peg post each side and a net drawn below it (`Builder.net()`, `sim.nets`, decoration only; marbles fall through). Preview test (6 min): 702 through, median 4.6 s, max 8.9 s, 2% touched no player, 0 rescues. Races: 600 short chi² 6.0 (3.5 lead changes); 600 last-one-standing 5.3; 300 medium 3.1; 100 with 30 names 28.4 (0 rescues); funnels on 3.9. 0 timeouts. After the faster kicks: 600 short of foosball×2 chi² 2.4; 300 last-one-standing of foosball, glass, foosball 4.4; 100 foosball×2 with 30 names 29.0; 300 random short 7.3. 0 rescues, 0 timeouts. Adding it to `TEMPLATES` changed every seed's course.
- **Glass Floors / Glass Tiles** (ids `glass`, `glasstiles`, built by `glassFloors()`). These are the "equalizer" sections: 4 floors of `Builder.breakaway()` glass. The first marble to land on a pane's top face is launched up at 8–9 m/s, and the pane stops colliding for good (`NO_GROUPS`, so the collider handle stays valid) and emits `shatter`. Glass Floors uses one full-width pane per floor. Glass Tiles splits each floor into 1–4 tiles, never the same count on two floors in a row. Tiles always span the whole width with 0.2 m seams, so nothing drops past a floor untouched. A sparse peg row sits between floors, and the highest bounce (~2 m) reaches it but never the floor above. Measured over 150 races: they are the only sections where the pack comes out tighter than it went in (time spread ×0.8, against ×1.2–1.8 elsewhere), and the leader changes across them about 62% of the time, with 0 rescues.
- **Trapdoor Floor** (id `trapdoors`; simplified at the user's request). Two floors (dy 5.5 and 11) of `TRAPDOOR_CELLS` = 3 cells, each cell a pair of doors that open together (`Builder.hatch()`, a trapdoor driven by a level function). Nothing sits above the top floor (no pegs or wall deflectors, user's request), so marbles drop straight onto it. On each floor one hatch is always open (user's request): `hatchRelay()` opens a random cell for a random 1.2–2.0 s (`TRAPDOOR_OPEN`), and 0.4 s before it starts closing opens a different random cell, so there's always a way through but never in a predictable place. The schedule is drawn lazily from its own `mulberry32` (seeded with one draw of the build rng), so it never runs out and replays match. The floor spacing was set for the original 4 m doors, whose tips hang ~3.9 m down. History, all measured over races of pegs → trapdoors → pegs with 6 names ("spread" = middle two-thirds of the pack, in → out; "flipped" = pairs leaving in the opposite order to how they went in):
  - Original: 2 cells per floor, every door on one period, the floors taking turns. Spread 1.42 → 1.71 s, leader's gap to the median 1.73 → 1.95 s, 47% flipped. The user found the group that made the first opening got away, a full period ahead.
  - Bottom floor on twice the period, so it collects two batches and drops them together: spread → 0.43 s (0.71 with 4 cells), leader's gap → 0.44 s, 69% flipped (57% with 4 cells), +1.7 s in the section. This worked best for keeping the pack together, but the user preferred random openings.
  - Staggered or random cell timings always spread the pack *more*, because marbles that arrive together then wait different times: 4 evenly staggered cells → 3.65 s (2.63 s on a 2–2.5 s period); a staggered top floor over a fully synced bottom floor → 2.36 s.
  - 3 cells, each on its own random period (4–5 s) and phase: spread 1.70 → 3.09 s, leader's gap 1.77 → 3.19 s, 36% flipped, median 5.7 s in the section, max 21.2 s. With 30 names the leader's gap goes 2.8 → 4.6 s (0.10 rescues). Removing the pegs above: trapdoors×2 300 short chi² 4.7; 30 names 42.2, then 36.8 and 19.4 on reruns.
  - Now (3-cell relay, no pegs above): spread 1.58 → 3.44 s, leader's gap 1.91 → 3.34 s, 34% flipped, median 3.7 s in the section (it's the quickest version), max 18.4 s. With 30 names the leader's gap goes 2.8 → 4.6 s, and 0.33 rescues per race on the pegs → trapdoors → pegs course (watch this). Tested: 300 short of trapdoors×2 chi² 3.2; 300 last-one-standing of trapdoors, pegs, trapdoors 2.4; 100 trapdoors×2 with 30 names 37.4 (0 rescues); funnels on with trapdoors, pinball, trapdoors 1.8; 600 random short 6.0. 0 timeouts.
- **Peg fields and the walls.** Peg rows end about 0.5 m short of each wall, which left a lane where a wall-hugging marble fell straight through untouched. `pegRows()` now adds wall deflectors between every other pair of rows (when there are 2+ rows), leaves out pegs within 1.05 of a deflector so nothing can wedge, and adds one peg past each deflector tip to cover the gap that leaves. Check new peg layouts for straight-drop lanes by testing each x against the static colliders in the band.
- **Photo-finish slow motion** (`isDramatic` in `main.ts`). In first-to-finish it triggers when the leader is in the last 7 m and the runner-up is under 2 m or about 0.3 s behind. It eases in fast and holds 0.9 s past the line. The old 5 m / 1.6 m test with slow easing missed some close finishes; the new one caught all 23 close finishes in a 400-race test. The test only looks at height, so the pair can be far apart sideways (common in Free Fall): `isDramatic` returns the pair, and the camera centres on their midpoint across and zooms in only as far as keeps both on screen with a 1.6 m margin (it may stay at 1×).
- **Continue watching.** The winner card's "Continue watching" button sets `watching`: the camera follows whoever is still racing, and a 🏆 Results button reopens the card. The card comes back on its own 1.5 s after the last marble finishes, and then the camera stays on the last finisher. With no target at all, the camera drifts back to the start gate.
- **Section guide and previews.** The setup card's 📖 Section guide (`src/ui/sections.ts`) lists every entry in `SECTIONS` (`course/index.ts`: segment templates, finishes, funnel guards) with a description, and its Preview shows one on the main stage as the `'preview'` screen in `main.ts`. `SimOptions.section` makes the sim build only that section via `buildSection()` (no gate, mixer or countdown; `finishY` is Infinity unless it's a finish). At the user's request a preview keeps dropping unnamed marbles in at random x along the top (`previewTick()` in `sim.ts`: every 0.3–0.7 s, at most `PREVIEW_MAX` = 24 at once). They're removed once they fall out of the bottom, or, in a finish, 1.5 s after crossing the line (marked `finished` without a place or winner, so no winner card). In a preview `sim.marbles` loses marbles as it goes, so `idx` is no longer the array position: look marbles up by `idx` (as `renderer.onEvent` does), and the renderer's `syncMarbles()` adds and removes their sprites. The Paddle Wheel and Valve guards reach the cap (a pile at the throat), and drops pause until marbles leave. `renderer.preview` frames the whole section, or auto-pans and lets the player wheel/drag when it's taller than about 30 m. A new template, finish or guard shows up in the guide automatically but needs a description in `ABOUT` in `sections.ts`.
- **Winner history.** Up to 100 winners are kept in `gd.history`. The setup card shows the latest 5, and "Show all" opens a `<dialog>`, which has the clear-all button behind a confirm step. While the dialog is open, the global hotkeys in `main.ts` are skipped (`setup.modalOpen`), so Space can't start a race behind it. Each entry also stores the race's options (`race`: names, seed, length, mode, funnels, finish). Clicking an entry (or Enter/Space on it) replays that race. Replays, including the winner card's "Replay this race", don't add the winner to the history again. Entries saved before this have no `race` and can't be clicked. A replay only matches the original while the sim code is unchanged, so each entry also stores `v`, the `__SIM_VERSION__` it ran on: a hash of every file in `src/sim/` (line endings normalised) plus the Rapier version, made in `vite.config.ts` at build/dev-server start, subfolders included (declared in `src/globals.d.ts`). Entries whose `v` doesn't match can't be replayed (at the user's request: no "may differ" replays), so **any** edit under `src/sim/`, even a comment, locks every saved race. Restart the dev server after sim edits to refresh the hash.
- **Rendering.** Static walls and pegs share one Graphics object. The zone layer must draw *above* static walls, or the conveyor belts get hidden. Name labels are drawn in screen space (overlay) so text stays crisp.
- **Standings.** The HUD reorders with hysteresis (needs a 0.35 m lead to swap places) and `sim.leader` also has hysteresis, so neck-and-neck marbles don't flicker.
- **Lead announcements** (user's request). A new leader only gets the `lead` event ("takes the lead" banner, sound, comeback check) and counts in `sim.leadChanges` once it has held `sim.leader` for `LEAD_HOLD` = 1 s of sim time. The crown still moves at once. This cut the counted lead changes from about 9.7 to 3.5 per short race (300 short races, chi² 4.9), so older lead-change figures in these notes are on the old, unheld count. In last-one-standing the board is "SAFEST FIRST" (hindmost on top) and crowns only show in first-to-finish mode.
