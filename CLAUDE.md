# Gravity Drop: notes for Claude

A gamified marble-race name picker. The user felt online wheel spinners lacked a physical, clicky feel and pick-from-a-hat tools weren't exciting. They asked for a **gravity race with lots of comebacks**, where the leader keeps changing because of things that spin, blow and move, not just static pegs. Keep that goal in mind for every change: more lead changes and more visible, clicky drama. The win odds must stay even.

The README covers setup, the deploy steps and the folder layout. The notes below are what the code doesn't show.

## Architecture rules
- **`src/sim/` must stay headless.** No Pixi and no DOM. The renderer and audio only read sim state and drain `sim.events`. That separation is what lets `scripts/fairness.ts` and `scripts/inspect.ts` run in Node.
- **Determinism.** The sim advances only in fixed `DT = 1/120` steps, and everything random uses `sim.rng` (mulberry32 seeded from `opts.seed`). The countdown is also counted in sim steps (`COUNTDOWN`), not wall-clock time. Never use `Math.random()` or real time inside `src/sim/`; doing so breaks "Replay this race". Slow motion (`timeScale` in `main.ts`) only changes how many steps run per frame.
- **Fairness.** Start slots are shuffled, and nothing in the sim ever picks a marble by name or index. Chaos events (lightning, lucky warps) were removed at the user's request: races are pure physics, so lead changes have to come from the course itself.
- **Coordinates.** 1 unit ≈ 1 m and y points down. The course is `W = 16` wide, with a gate at y = 4, followed by stacked segments, the finish funnel and a basin. Walls are capsules (rounded joints, so marbles never snag). Collision handles are tagged via `sim.tag()` to drive sounds and bumper behaviour.
- **Race length** is a count of random segments, 1–15 (`MIN_SEGMENTS`/`MAX_SEGMENTS` in `course.ts`), with the finish added on top (the setup screen says "segments + finish"). Short/Medium/Epic are presets of 5/10/15 (`SEGMENT_COUNTS`). `SimOptions.length` takes a preset name or a number, and `segmentCount()` in `sim.ts` resolves and clamps it. The setup screen stores a number and migrates old saved preset names. There are only 10 segment templates, and `pickSegments` reuses them (never back-to-back), so a long race repeats sections.
- **Adding a segment.** Add a template to `TEMPLATES` in `course.ts`, built only from `Builder` primitives and zones, then run the stall checks below.
- **Finishes.** Every course ends with a finish from `FINISHES` (`funnel`, the slingshot funnel with a short flipper at the bottom of each wall, `halfpipe` and `freefall`) straight under the last segment. A finish has `h` (including the basin), `finish` (the finish line's offset) and `build`, and holds the finish line and the basin. Its top must leave room for whatever the last segment ends in. `buildCourse` always draws one rng value to pick it, so a seed builds the same segments whichever is forced (`SimOptions.finish`, the setup screen's Finish setting, or the fairness script's 7th argument). It is its own HUD segment, named `FINISH · <name>`.
- **No more finales** (user's request). There used to be a finale between the segments and the finish: Final Pinball (now the `pinball` segment template, "PINBALL") and Final Mayhem (removed completely, along with the setup screen's Final drop setting and the fairness script's finale argument). Removing them changed every seed's course. Tested after: 600 short chi² 2.0 (25.7 s races, down from ~36 s; 9.7 lead changes, down from 12.7, as Mayhem was a big source of them); each finish forced, 300 short, chi² 0.8–6.9; 600 last-one-standing 4.8; 300 medium 1.8 (16.2 lead changes); 100 races with 30 names 31.4 (bound 44.2); 600 short with funnels 4.8. All 0 rescues, 0 timeouts.
- **Half-pipe finish** (id `halfpipe`, added on the user's request as a variant; not yet fairness- or stall-checked). A Λ roof sends everyone out to the walls, then a parabolic bowl (2.4 m deep, 8 capsule segments a side) slopes down to a drain hole 1.4 m clear (so two marbles can't arch across it). A fast marble jumps the hole and swings up the far side; a slow one drops in. The roof sits above the rims, so a swinging marble can't reach it.
- **Free Fall finish** (id `freefall`; the user's idea: the feeling of going really fast without a really long drop). It's 40 m to the line (the user doubled it from 20 m). A `SkyZone` (`Builder.sky()`) covers the whole finish down to the line. It cancels gravity and eases each marble's fall toward 2.5 m/s (`ease` 0.012 per step, so extra speed bleeds off over about 0.7 s), and adds a gentle sideways gust that varies with height and time. Sideways speed has its own light damping (`drag`, `FREEFALL_DRAG` = 0.001 per step, a half-life of about 6 s): the user wanted marbles that come in at an angle to keep it, instead of straightening into a vertical drop (it used to be `ease * 0.5`). Marbles now bounce off the side walls often (about 3 in 4 get within 0.8 m of one), but nothing pins them there. The renderer draws speed lines streaking up through it at about 30 m/s, so the slow fall reads as fast.
- **Free Fall boost pads rise** (user's request: fixed pads broke the illusion of speed). A `RiserZone` (`Builder.risers()`) spawns 2.8 × 0.6 m downward pads (`FREEFALL_PAD_W`; the user doubled it from 1.4 m, and the renderer adds a chevron column per 1.4 m of width) (10 m/s, keeping the marble's sideways speed) at random x along its bottom edge every 0.3–0.7 s, and they stream up at 20 m/s (`FREEFALL_RISE`, the slow end of the speed lines) until they leave the top. Spawns come from the zone's own `mulberry32`, seeded with one draw of the build rng, and its clock counts sim steps, so replays match. Pad centres are spread over the full width and then pushed back inside, so wall-riders meet as many pads as anyone (with plain uniform x they got 1.42 boosts against 1.62). Because the pads move much faster than the marbles, how many a marble meets hardly depends on its own speed, so one boost doesn't make the next more likely. That replaced fixed rows (2 per row, 4 m apart, never in the column the row above used), which were spaced out to make chaining harder. Measured over 200 races with 2.8 m pads: 2.92 boosts per marble (1.91 with 1.4 m pads), none get zero, 93% get 2 or more, 9.0 s spent in the finish. Tested with it forced at 2.8 m: 600 short chi² 2.2 (31.9 s races, 9.8 lead changes); 600 last-one-standing 4.8; 100 with 30 names 36.8 (bound 44.2; 32.0–38.6 at 1.4 m); funnels on 3.3. 0 rescues, 0 timeouts. There's no funnel at the user's request: marbles fall straight to the line, with only the usual basin below it. With the old 20 m version the first marble into the finish still won about 81% (90% for the funnel, 76% for the half-pipe), because the leader usually arrives over a second ahead; that hasn't been re-measured since the changes.
- **Rejected finishes.** The user tried and removed a Water Wheel (a slow 8-spoke windmill; the first marble in won only 58%, but it "wasn't sparking joy") and a Ski Jump (a takeoff over a pit, where fast marbles overshot onto a landing hill and had to roll back; not the feeling the user wanted). The stats were fine for both; what the user is after is how a finish *feels*, so check with them before tuning a finish for numbers alone.

## Traps hit so far
- **Infinite loops in segments.** Fans that covered a whole ramp and outpowered gravity pinned marbles against a wall forever, and reversing belts plus pop-back boosters recycled them. The rule now: force zones cover only a *window* of a ramp, belts are weak (`0.025` blend per step), and back-boosters have long cooldowns. There are two safety nets: an anti-stall nudge after 3.5 s motionless, and a `rescue()` after 20 s with no progress (counted in `sim.rescues`). Keep rescues rare, about 0.05–0.3 per race.
- **No top-level `await` in `main.ts`.** Pixi lazy-loads chunks that import back into the entry module, so a top-level await deadlocks the *production* build (a blank page with no errors). Startup lives in `async function boot()`.
- **Funnels.** With `opts.funnels`, `buildCourse` adds a 5.5 m funnel to the bottom of every segment except the last (it is counted in that segment's `h`) and picks a guard from `FUNNEL_GUARDS`. It only draws from the rng when funnels are on, so old seeds without funnels still build the same course. Never put a spinner *above* a throat: its tips batted marbles back up the funnel slope forever (rescues went from 0.05 to 1.5+ per race). Guards must keep the throat moving; never use a static plug, and must fit inside `FUNNEL_H` (the paddle wheel once reached into the next segment and swept through its pegs).
- **Removed sections.** The Factory, The Elevator, Pinball Parlor and the Portal Maze were taken out at the user's request, and Windmill Alley was merged into the Windmill Grinder. Flippers are used by the Pinball segment and the funnel finish. Conveyors, stampers, the lift, the see-saw and portals are unused since Final Mayhem was removed; their `Builder` primitives are kept.
- **Teleports reset the no-progress clock.** A back-portal or a lift ride restarts `bestY`/`bestT` from the new spot. Before that, a marble sent back was "rescued" (dropped forward) after 20 s if it had not caught up, which undid the setback.
- **Funnel flippers.** The funnel finish puts a 1 m flipper at the bottom of each funnel wall. The drain between their tips stays about 3.5 m wide and they flick every 1.6-2.4 s; tested with no extra rescues. The Pinball segment's flippers flick every 1.0-1.6 s.
- **Windmill Grinder** (id `grinder`). It is alternating rows of windmills, with one big windmill and two medium ones in the middle and no funnel (the user asked for the hopper to be removed). Windmill tips stay at least 0.9 m from each other and from the walls, so nothing gets pinched.
- **Switch Maze** (id `switches`; it replaced the Portal Maze, which the user found to be just a peg garden with portals). A funnel feeds a flip-flop switch (`Builder.toggle()`: a plate pivoted at its centre and tilted 0.6 rad), which feeds two funnels with a switch each, then four 4 m lanes in a shuffled order: two glass floors (no pegs between, at the user's request), pegs with wall ledges, a 3-bar windmill, or three zigzag shelves. A switch flips when a marble *enters* the band under its open tip (entry only, so a slow marble can't flip it twice); marbles that arrive mid-swing pass without flipping it (about 1.6 flips per marble against a maximum of 2). Traps found while building it: gaps just under a marble's width between lane pegs or shelves and the walls stalled marbles, so every gap is either ≥ 0.75 m clear or closed; and two marbles arched across a throat (one hanging on the throat wall, propped on one sitting on the plate) for 10+ s, which is why the throat walls are only 0.3 m and the plate sits 1.5 m below the throat. Glass pane bounces (~2.25 m) must stay below the switch's trigger band. Tested: 600 short races chi² 3.3, 0 rescues, 12.7 lead changes; 30 names 0 rescues.
- **Black holes (unused, kept for later at the user's request).** `BlackHoleZone` / `Builder.blackHole()`: a back-portal horizon inside a gravity well whose pull rises toward the centre, with a sideways swirl, optionally drifting along a `Track`. It emits a `portal` event with `hole: true` (its own effect and ticker text). It was tried in "Black Hole Switchbacks" (zigzag ramps); the user liked the obstacle but not the section. A hole 1.35 m above a ramp with a 2.2 m well and 34 m/s² pull swallowed about 0.4 marbles per pass. Its drawing is done in a scaled-up local frame, because Pixi tessellates circles by local radius and world-unit circles looked polygonal.
- **Glass Plug funnel guard** (id `glass`). A single `breakaway()` pane across the throat: the first marble is launched back up the funnel (kick 7.5–8.5, apex ≈ 1.8 m with g = 18, inside the 3 m funnel) and the pane is gone, so it's never a lasting plug. Adding it changed the guard shuffle, so funnels-on seeds from before it build different courses. Tested: 600 short races with funnels, chi² 2.3, 0 rescues; 30 names, 0.47 rescues per race.
- **Rows of bumpers act as a ceiling.** A horizontal row of bumpers with gaps of about 1 m kicks nearly every marble back up. One near the finish funnel (under the old Final Pinball) caused about 1.4 rescues per race. Keep gaps within a row at 1.5 m or more.
- **Valve funnel guard** (id `valve`). At the trapdoors' usual open angle (1.35 rad) its door tips were left about 1.1 m apart, narrower than two marbles side by side (1.28 m). Pairs jammed there until the doors closed and knocked them back up the funnel, which also caused most of the roughly 1.3 rescues per race in 30-name runs. At the user's request the doors now open further (`VALVE_SWING` = 1.65 rad, a touch past straight down, through `trapdoor()`'s `swing` argument) and stay open longer (62–72% of each cycle, up from 50–60%). In a 6-minute preview test, 684 marbles got through instead of 450, 29 were knocked back up instead of 132, and there were 0 rescues instead of 10. With funnels on: 300 short races chi² 6.0, 300 last-one-standing chi² 7.1, and 100 races with 30 names chi² 35.0 (bound 44.2) at 0.10 rescues per race.
- **Plain funnel guard** (id `plain`, added at the user's request): an empty throat. Adding it changed the guard shuffle again, so funnels-on seeds build different courses than they did before.
- **Start mixer.** The start box (`mixer()` in `course.ts`) has a lid at `sim.mixerTop` and four sweeping floor jets (`FanZone.until`/`sweep`) that run only during the countdown. It is built *after* the segments so seed → course layout didn't change. Plain alternating jet tilts only made marbles bounce in place (about 90% of left-to-right order survived); the sweep brings that down to about 62% with 6 marbles. During the countdown the camera holds on the box, the standings board is frozen and no crown is shown.
- **Pinball** (id `pinball`; rebuilt at the user's request to look like a real machine). The playfield is rows of 2, 1, 2, 3, 2 bumpers, all r 0.6 and widely spaced (the user wants them big and spread out, not more of them), with plain bars on the walls at y 4.8 and 10.6 that turn wall-huggers back in. The lower table starts at `PINBALL_LOW` = 13.5: on each side an inlane guide runs from 1 m off the wall down to a 1.5 m flipper's hinge, so the guides funnel everything to the flippers and a drain ~2.2 m clear between their tips. A `Builder.sling()` stands in front of each flipper, off the walls, with ~0.85 m of inlane clear behind it (the user wanted marbles able to go behind the slings). The gap between the wall and each guide is an outlane (~0.85 m clear, open below) that lets a lucky marble skip the flippers: about 9% of marbles take one (the wall bars keep it low). In a 10-minute preview test: median 5.5 s through the section, max 24 s, 0 rescues. Full races after the rebuild: 600 short chi² 5.0 (9.3 lead changes); 600 last-one-standing 6.9; 300 medium 0.8; 100 with 30 names 41.6 (bound 44.2); funnels on, 600 short 2.3 and 100 with 30 names 14.6 (0.08 rescues). 0 timeouts. `Builder.sling()` kicks marbles off its upward-facing side on contact start (handled in `marbleHit`, like bumpers); the funnel finish also uses slings on the middle stretch of its walls, leaving the wall by the throat plain so marbles settle out instead of being kicked back and forth.
- **Trampoline Park pads.** `Builder.tramp()` pads re-launch marbles off their top face (handled in `marbleHit`). The first tuning had marbles hopping sideways from pad to pad along a single row: each bounce carried them about as far as the gap between pads, and crossing the segment took about 9.6 s. Keeping the bounce speed low (3.5 m/s minimum, 5.5–6.5 m/s cap) and the sideways carry at 0.75 brought that down to about 5.6 s. Keep the highest bounce (v²/2g) below the 2.2 m spacing between rows, so a marble can't bounce back up onto the row above.
- **Pendulum Swing** (id `pendulums`). `Builder.pendulum()` hangs a bumper ball on a rod. Only the ball is solid: the rod collider is a sensor with `NO_GROUPS`, kept only so the renderer can draw it (the user asked that marbles pass through the rods). A bumper tag can carry `collider`/`kick`/`swing`, so `marbleHit` reads the ball's live position and adds its swing velocity. The kick is soft (6.5–7.5 m/s against the usual 11) so marbles aren't juggled back up into the row 2.6 m above. Rows of 4 and 3 balls alternate; swinging balls stay about 0.9 m apart and from the ledges. The walls use fixed ledges only (short ones on the rows of 4, 2.6 m ones on the rows of 3), so nothing within 3.5 m of a wall is ever open. Moving balls leave a middle lane open for a moment now and then, but in 600 test passes no marble fell through without hitting something.
- **Glass Floors / Glass Tiles** (ids `glass`, `glasstiles`, built by `glassFloors()`). These are the "equalizer" sections: 4 floors of `Builder.breakaway()` glass. The first marble to land on a pane's top face is launched up at 8–9 m/s, and the pane stops colliding for good (`NO_GROUPS`, so the collider handle stays valid) and emits `shatter`. Glass Floors uses one full-width pane per floor. Glass Tiles splits each floor into 1–4 tiles, never the same count on two floors in a row. Tiles always span the whole width with 0.2 m seams, so nothing drops past a floor untouched. A sparse peg row sits between floors, and the highest bounce (~2 m) reaches it but never the floor above. Measured over 150 races: they are the only sections where the pack comes out tighter than it went in (time spread ×0.8, against ×1.2–1.8 elsewhere), and the leader changes across them about 62% of the time, with 0 rescues.
- **Peg fields and the walls.** Peg rows end about 0.5 m short of each wall, which left a lane where a wall-hugging marble fell straight through untouched. `pegRows()` now adds wall deflectors between every other pair of rows (when there are 2+ rows), leaves out pegs within 1.05 of a deflector so nothing can wedge, and adds one peg past each deflector tip to cover the gap that leaves. Check new peg layouts for straight-drop lanes by testing each x against the static colliders in the band.
- **Photo-finish slow motion** (`isDramatic` in `main.ts`). In first-to-finish it triggers when the leader is in the last 7 m and the runner-up is under 2 m or about 0.3 s behind. It eases in fast and holds 0.9 s past the line. The old 5 m / 1.6 m test with slow easing missed some close finishes; the new one caught all 23 close finishes in a 400-race test.
- **Continue watching.** The winner card's "Continue watching" button sets `watching`: the camera follows whoever is still racing, and a 🏆 Results button reopens the card. The card comes back on its own 1.5 s after the last marble finishes, and then the camera stays on the last finisher. With no target at all, the camera drifts back to the start gate.
- **Section guide and previews.** The setup card's 📖 Section guide (`src/ui/sections.ts`) lists every entry in `SECTIONS` (`course.ts`: segment templates, finishes, funnel guards) with a description, and its Preview shows one on the main stage as the `'preview'` screen in `main.ts`. `SimOptions.section` makes the sim build only that section via `buildSection()` (no gate, mixer or countdown; `finishY` is Infinity unless it's a finish). At the user's request a preview keeps dropping unnamed marbles in at random x along the top (`previewTick()` in `sim.ts`: every 0.3–0.7 s, at most `PREVIEW_MAX` = 24 at once). They're removed once they fall out of the bottom, or, in a finish, 1.5 s after crossing the line (marked `finished` without a place or winner, so no winner card). In a preview `sim.marbles` loses marbles as it goes, so `idx` is no longer the array position: look marbles up by `idx` (as `renderer.onEvent` does), and the renderer's `syncMarbles()` adds and removes their sprites. The Paddle Wheel and Valve guards reach the cap (a pile at the throat), and drops pause until marbles leave. `renderer.preview` frames the whole section, or auto-pans and lets the player wheel/drag when it's taller than about 30 m. A new template, finish or guard shows up in the guide automatically but needs a description in `ABOUT` in `sections.ts`.
- **Winner history.** Up to 100 winners are kept in `gd.history`. The setup card shows the latest 5, and "Show all" opens a `<dialog>`, which has the clear-all button behind a confirm step. While the dialog is open, the global hotkeys in `main.ts` are skipped (`setup.modalOpen`), so Space can't start a race behind it.
- **Rendering.** Static walls and pegs share one Graphics object. The zone layer must draw *above* static walls, or the conveyor belts get hidden. Name labels are drawn in screen space (overlay) so text stays crisp.
- **Standings.** The HUD reorders with hysteresis (needs a 0.35 m lead to swap places) and `sim.leader` also has hysteresis, so neck-and-neck marbles don't flicker. In last-one-standing the board is "SAFEST FIRST" (hindmost on top) and crowns only show in first-to-finish mode.

## Verifying changes
- `npx tsc --noEmit` then `npm run build`.
- Fairness and stuck checks: `npm run fairness -- 600 short first 6 5000` (args: races, length (preset or 1–15), mode, names, seedOffset, funnels 1/0, finish random/funnel/halfpipe/freefall). Expect chi² under the printed bound, **0 timeouts**, and about 5–12 lead changes per race. Also check `last` mode, `medium` length, 30 names and funnels on after any physics or course change. A single high chi² can be noise, so rerun with a different seedOffset before chasing a bias.
- One seed in detail: `npx tsx scripts/inspect.ts <seed> [length] [names] [seconds] [funnels]` prints the segment layout, event counts and final marble positions (useful for finding where marbles get stuck).
- Visual check: run `npx vite preview --port 4173` and screenshot with `puppeteer-core` driving the installed Chrome (`C:/Program Files/Google/Chrome/Application/chrome.exe`, args `--use-angle=swiftshader --enable-unsafe-swiftshader`). Install puppeteer in the scratchpad, not in this project. Preset settings via `localStorage` key `gd.settings`, e.g. `{"length":"short","mode":"first"}`, and names via `gd.names`. Check both 1600×900 and 390×844 (phone). Headless frame rates of about 20–50 fps are normal with software rendering.

## Environment quirks (Windows, Git Bash tool)
- `node -e '…'` has silently done nothing in this shell. Write a script file and run that instead.
- `pgrep` isn't available, and sed replacements containing `$&` mangled code once. Prefer the Edit tool for code changes.
